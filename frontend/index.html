      ARCHITECTURE ANALYSIS

      Failure & Recovery Analysis

      How StreamPulse handles likely component failures, what the code can detect, and where recovery still needs an operator.

      ARCHITECTURE REFERENCE

      Describes possible failure paths and implemented safeguards; it does not run failure simulations or show live component status.

      EVENT & METRIC PATH

      How the components connect

      Current StreamPulse architecture

      FastAPI

      Publishes events and reads metrics and service status.

      publishes
      02 · BROKER

      RabbitMQ

      Queues published events for the consumer.

      delivers
      03 · PROCESSOR

      Consumer

      Validates deliveries, updates windows, and records measurements.

      writes
      04 · STORE

      Holds current summaries, monitoring snapshots, and bounded samples.

      Run definitions, lifecycle state, and finalized results are stored in SQLite. FastAPI reads current metrics and monitoring data from Redis.

      CConsumer Failure & RecoverySeparate process · receives and processes queued eventsPROCESSOR

      01Component role

      The separate run_consumer.py process receives RabbitMQ events, validates them, updates the tumbling and sliding windows, and writes available summaries and measurements to Redis.

      02Possible failure scenarios

      The process or host can stop during a delivery; event decoding or processing can fail; Redis or SQLite can be unavailable while a run-scoped delivery is being handled.

      03System impact

      Consumption pauses while no consumer is active. Window buffers live in process memory and are lost on restart. Previously written Redis summaries may still be available, but the code does not archive them elsewhere and partial windows are not restored.

      04Failure detection IMPLEMENTED

      The consumer writes a Redis heartbeat; GET /api/monitoring reports consumer state and freshness. Callback failures are logged and reflected in counters when those writes succeed.

      05Recovery strategy

      IMPLEMENTED The consumer connects with aio_pika.connect_robust, uses manual acknowledgements, and requeues selected transient failures. Run-scoped durable reservations can be settled after redelivery.

      OPERATOR ACTION Restart a process that has exited and inspect any pending reservations. This repository does not supervise or automatically restart the consumer process.

      06Data integrity

      A delivery can be redelivered, so processing is at-least-once-oriented; exactly-once processing is not guaranteed. SQLite run receipts preserve processing outcomes, but in-memory window contents can be lost. Messages rejected without requeue may be discarded because this project does not declare a dead-letter exchange.

      RRabbitMQ Failure & RecoveryMessage broker · transports events from API to consumerBROKER

      01Component role

      RabbitMQ transports published library events from FastAPI to the separate consumer.

      02Possible failure scenarios

      The broker may be unreachable, a connection may drop during publish or delivery, a publisher confirmation may be lost, or the queue may accumulate messages while no consumer is active.

      03System impact

      Publish requests can fail or have an uncertain outcome. Consumption can pause and queued work can be delayed. An uncertain publish cannot safely be assumed accepted or rejected.

      04Failure detection IMPLEMENTED

      The API health and monitoring endpoints expose RabbitMQ availability and queue-ready/consumer counts when inspection succeeds. Publisher failures are returned through API error responses; run accounting can retain an unknown publish outcome.

      05Recovery strategy

      IMPLEMENTED The publisher uses a robust connection, publisher confirms, persistent messages, and a durable queue. The consumer uses a durable single-active-consumer queue with manual acknowledgements.

      OPERATOR ACTION Restore broker service and verify queued work and uncertain run reservations. No broker failover deployment or operator alerting is configured by this repository.

      06Data integrity

      A connection loss after publish begins can leave acceptance unknown. Run reservations remain pending rather than being republished automatically, avoiding an automatic duplicate. Acknowledgement loss can still cause redelivery. The project does not claim zero message loss or exactly-once effects.

      RRedis Failure & RecoveryMetrics store · configuration, summaries, monitoring and samplesDATA STORE

      01Component role

      Redis stores current window summaries, active and pending window configuration, monitoring snapshots, and bounded run-scoped and overall measurement samples.

      02Possible failure scenarios

      Redis may be unreachable, a write or read can time out or fail, stored configuration can be invalid, or expiring measurement keys can no longer be read.

      03System impact

      Health and monitoring can report Redis unavailable. A window-summary write failure can cause consumer processing to fail. Measurement writes are best effort, so events can be processed without corresponding latency samples; final results may then be incomplete.

      04Failure detection IMPLEMENTED

      GET /api/health reports service status; GET /api/monitoring reports Redis status, consumer heartbeat, and the consumer's last observed aggregation-write state. Storage errors are logged or returned as unavailable responses.

      05Recovery strategy

      IMPLEMENTED Callers expose failed reads/writes and keep monitoring/measurement writes best effort where coded. At consumer startup, the active window configuration is read from Redis or initialized if absent.

      OPERATOR ACTION Restore Redis and restart or re-establish affected processes as appropriate. This repository does not implement a Redis recovery orchestrator or a historical measurement archive.

      06Data integrity

      Do not treat missing Redis measurements as zero. Measurement keys are bounded and expire; Redis summaries are not the durable run-result record. Finalized run results are persisted in SQLite, but their measurement completeness depends on the data available when finalization runs.

      FFastAPI Failure & RecoveryHTTP API · validates requests and manages runsAPI SERVICE

      01Component role

      FastAPI serves the frontend, validates API requests, persists experiment and run state in SQLite, and publishes events through RabbitMQ. A bounded workload runner is launched as an in-process task after a run is started.

      02Possible failure scenarios

      The API process or host can stop, SQLite can be unavailable, or an API request can fail while publishing or creating a run. An in-process runner can be cancelled or interrupted during shutdown.

      03System impact

      HTTP actions and reads are unavailable while the service is down. The recent-event display is process-local and resets with the process. SQLite records persist on disk, but a runner task is not a separate durable job queue.

      04Failure detection IMPLEMENTED

      GET /api/health reports API availability and service configuration status. Routes return validation or service errors for handled failures, and background task failures are logged by exception type.

      05Recovery strategy

      IMPLEMENTED Graceful shutdown cancels and awaits runner tasks and tracked finalizers; execution claims and interruption records keep unsafe work fail-closed.

      OPERATOR ACTION Restart the API process after its dependencies are available and inspect interrupted runs. No external process supervisor, replicated API service, or automatic run resumption is implemented here.

      06Data integrity

      SQLite-backed experiment, run, and finalized-result records survive an API process restart when the same database path is used. In-memory recent events do not. A client timeout does not prove that a request had no effect; clients should read persisted state before retrying a non-idempotent action.

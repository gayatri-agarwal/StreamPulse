06 · CONCEPTS IN CONTEXT

What to observe

Why can a burst create a backlog?

The generator can publish a burst faster than the single active consumer processes messages. RabbitMQ's ready count may rise, then fall as the consumer catches up. The count is a point-in-time observation.

What do the windows summarize?

Tumbling windows emit for complete fixed-size groups. Sliding windows recalculate over the latest configured event count. Both are event-count-based and consume messages in delivery order.

Event time versus processing time

Event time is the timestamp carried by the event. Published time marks when the API begins its publish attempt; processed time is recorded after the consumer completes processing. Late mode can make these visibly different.

What happens to a late event?

It enters the same consumer path in its actual RabbitMQ arrival order. Existing windows do not use watermarks or allowed lateness, and a completed tumbling window is never reopened or revised.

Educational limitation: Late-Arriving mode demonstrates older, out-of-order event timestamps only. It is not true event-time window processing.

CConsumer Failure & RecoverySeparate process · receives and processes queued eventsPROCESSOR

What it does

The consumer validates deliveries, measures processing, updates in-memory windows, and writes available summaries to Redis.

Safeguards and limits

RabbitMQ uses manual acknowledgements and prefetch one. Selected failures requeue; permanent invalid messages are rejected without requeue. Window buffers are lost on consumer restart; delivery is at-least-once-oriented.

Operator response

Restore or restart the consumer when needed, inspect the queue, and review pending run reservations. The repository does not supervise the process or guarantee exactly-once effects.

RRabbitMQ Failure & RecoveryMessage broker · transports events from API to consumerBROKER

What it does

The API publishes persistent messages to a durable single-active-consumer queue with publisher confirms and mandatory routing.

Safeguards and limits

A lost connection after publishing begins can leave acceptance unknown. Queue monitoring reports ready messages and consumer count; unacknowledged counts are unavailable. No project-configured dead-letter exchange exists.

Operator response

Restore broker connectivity and inspect queued work. Do not interpret an unknown publish outcome as confirmed or failed without evidence.

RRedis Failure & RecoveryMetrics store · configuration, summaries, monitoring and samplesDATA STORE

What it does

Redis stores window summaries, configuration, monitoring snapshots, and bounded measurement samples.

Safeguards and limits

Monitoring and measurement writes are best effort where implemented; summary write failures can fail processing. Missing measurements are not zero, and in-progress windows are not persisted.

Operator response

Restore Redis, then verify monitoring and summaries. Run results remain in SQLite, but their completeness depends on measurements available before finalization.

FFastAPI Failure & RecoveryHTTP API · validates requests and manages workloadsAPI SERVICE

What it does

FastAPI validates events, publishes through RabbitMQ, serves monitoring, and manages SQLite-backed experiment lifecycle operations.

Safeguards and limits

Run stop requests close ingestion and use durable stop intent, reservations, settlement, and finalization safeguards. In-process simulation generator tasks do not survive an API restart.

Operator response

Restore the API and dependencies, inspect run state before retrying non-idempotent operations, and verify simulation status after restart.
